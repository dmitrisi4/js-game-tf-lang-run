## Recommended Data Sources

Primary terrain source:
- IGN/CNIG PNOA LiDAR-derived MDT/DTM.
- Start with `MDT02` / 2 m DTM for manageable city mesh resolution.
- Evaluate 3rd coverage `MDT/MDS v1` for Canarias where available; use higher resolution as source only, then downsample.
- Data policy: IGN/CNIG geospatial products are compatible with CC-BY 4.0 and require attribution.
- Source references:
	- https://www.ign.es/web/politica-datos
	- https://pnoa.ign.es/pnoa-lidar/tercera-cobertura

Primary vector source:
- OpenStreetMap via local Overpass/GeoJSON exports.
- Use ODbL attribution and keep derived database obligations explicit.
- Existing local files are sufficient for first-pass roads and building footprints.
- Source reference:
	- https://www.openstreetmap.org/copyright

Optional shoreline/water source:
- IDECanarias/GRAFCAN topobathymetric model, 2.5 m continuous land-sea model.
- Use when city coastline and water edge need better matching than the DTM-only terrain.
- Source reference:
	- https://www.idecanarias.es/listado_servicios/topobatimetrico

Rejected or fallback sources:
- Google Maps/Earth imagery or geometry: rejected unless explicit legal permission exists.
- Copernicus GLO-30/OpenTopography global DEM: fallback only; too coarse for street-level Puerto terrain.
- AI-generated city layout: acceptable only for filler props, not for geographic terrain/roads.

## Target Coordinate Model

Use one local projected space for terrain, roads, buildings, textures, and runtime placement:

- Source CRS for processing: Canary Islands projected CRS, preferably REGCAN95 / UTM zone 28N when supported by source data.
- Runtime X/Z: local meters multiplied by `metersToWorld`.
- Runtime Y: use the same scale policy as X/Z unless explicitly choosing vertical exaggeration.
- Origin: keep the existing road projection center unless a measured terrain alignment requires moving it.
- Axis convention:
	- runtime `x`: east/west
	- runtime `z`: north/south, matching current `projectTenerifeLonLatToWorld`
	- Blender conversion must preserve this convention through export.

Important decision:
- Prefer aligning the terrain to the existing road projection first, not reprojecting roads blindly.
- If the DTM crop reveals that the existing road center is wrong, update the projection and rebuild `roads-runtime.json` from source.

## Runtime Architecture Decision

Recommended architecture:

1. Add `PuertoCityTerrain` as a new component instead of overloading `TenerifeIslandPreview`.
2. Keep `ground1` as the stable runtime terrain mesh name because roads, buildings, and reset code already use it.
3. Load the baked road texture as the terrain material base layer.
4. Keep current road ribbon meshes behind a debug or close-range overlay flag:
	- disabled by default once baked road texture is validated
	- enabled for comparison, lane accents, or close-range edge crispness
5. Keep generated roadside buildings visual-only until a radius/primitive collision strategy is documented.

## Terrain Mesh Budget

Prototype target:
- AOI: current road bbox plus `150-300 m` buffer.
- DTM input: 2 m preferred, resample to `4-8 m` for first runtime mesh.
- Visual terrain mesh: target `50k-200k` vertices.
- Physics terrain: static mesh acceptable only for terrain queries; document it as static environment mesh.

Final target:
- Streamed/LOD terrain tiles if vertex count exceeds browser budget.
- Separate visual mesh and simplified collision mesh if terrain physics becomes expensive.

## Texture Budget

Prototype target:
- `2048 x 2048` albedo atlas for the city patch.
- `2048 x 2048` road mask if roads are mixed in shader/material.
- `1024 x 1024` contact sheet for albedo/mask QA.
- Mipmaps enabled for all world textures.

Final target:
- `4096 x 4096` city atlas only after browser memory and load timing are measured.
- Prefer WebP/KTX2 for color textures when the project pipeline supports it.
- Keep masks lossless or high-quality enough to avoid road edge artifacts.
